# [러쉬에잇 코딩 과제] 게임 로그 적재 파이프라인 설계 & 집계 API 구현 — 과제 원문

> 이 파일은 과제 안내문 원문을 그대로 보관하는 기준 문서다.
> AI 도구가 작업 중 요구사항을 임의로 해석·변경하는 것을 막기 위한 단일 기준(single source of truth)이며,
> 이 파일은 절대 수정하지 않는다. 해석·가정은 assumptions.md에, 설계는 design.md에 기록한다.

---

본 과제는 두 문제로 구성됩니다.

- 문제 1: 제약이 있는 전송 환경에서 RPG 게임 로그를 적재하는 파이프라인을 설계하고, 설계 문서를 작성하여 제출합니다. 코드 구현은 포함하지 않습니다.
- 문제 2: 문제 1에서 설계한 적재 서버를 구축하고, 적재된 데이터를 집계, 조회하는 API까지 구현하여 제출합니다.

문서는 [공통 명세]→[문제1]→[문제2]→[공통, 제출 및 안내] 순으로 구성됩니다.
주어진 제약 조건과 시나리오에서 설계 내용과 근거, 트레이드오프를 평가합니다.
명세에 정의되지 않은 사항은 합리적으로 가정하고, 가정한 내용을 문서에 명시해 주세요.

## [공통 명세]

### 시나리오

어떤 RPG 게임에서 발생하는 유저 행동 로그(레벨업, 몬스터 처치, 결제 등)를 수집하여 운영·분석에 활용하려 합니다.
단, 로그를 내보내는 전송측(게임 클라이언트/서버)은 제약이 있는 HTTP 클라이언트 환경입니다.
발생하는 게임 이벤트를 유실 없이 적재하는 파이프라인을 설계하는 것이 목표입니다.

### 전송 환경 제약 (핵심 제약)

| # | 제약 | 내용 |
|---|---|---|
| 1 | 프로토콜 | 로그 적재는 HTTP 프로토콜만 가능 |
| 2 | 요청 횟수 제한 | 1분당 120회까지 요청 가능. 초과 시 30초간 HTTP 요청 불가(차단) |
| 3 | 타임아웃 | 각 요청의 timeout은 30초 |
| 4 | 포트 | 80, 443 포트만 지원 |
| 5 | 응답 버퍼 | 수신 가능한 응답 본문 최대 10MB |
| 6 | 요청 본문 | 전송 가능한 요청 본문 최대 4MB |

### 상세 제약

- 위 요청 제한은 전송측(게임 인스턴스) 1개 기준입니다.
- 인스턴스 1개당 최대 30명이 참여합니다.
- 전체 동시접속자는 300명으로 가정합니다.
- 재시도로 인해 동일 로그가 중복 전송될 수 있습니다.
- 적재 측은 같은 event_id가 여러 번 들어와도 데이터가 중복되지 않도록 처리해야 합니다.
- 이벤트는 시간순으로 정렬되어 도착하지 않습니다.
- 모든 요청에는 인증 토큰/API 키 헤더가 필요하며, 인증되지 않은 혹은 위조된 요청은 거부되어야 합니다.
- 80/443 중 443(HTTPS) 사용을 권장합니다.

### 입력 이벤트 명세

로그는 다음 공통 envelope 구조를 가진 JSON 이벤트입니다.
한 번의 HTTP 요청에 다수의 이벤트가 어떻게 담기는지는 전송 방식 설계의 일부입니다.

#### 공통 envelope

| 필드 | 타입 | 설명 |
|---|---|---|
| instance_id | string (UUID) | 전송 인스턴스 ID |
| event_id | string (UUID) | 이벤트 고유 ID |
| event_type | string (enum) | 아래 이벤트 타입 중 하나 |
| user_id | integer | 계정 ID |
| character_id | integer | 캐릭터 ID (계정당 여러 캐릭터 가능) |
| session_id | string | 로그인 세션 ID |
| channel_id | string | 게임 채널/서버 인스턴스 ID (전송 단위) |
| payload | object | 이벤트 타입별 추가 속성 |
| occurred_at | string (ISO8601, UTC, ms) | 이벤트 발생 시각 |

#### 이벤트 타입

각 이벤트의 payload(타입별 상세 필드)는 지원자가 직접 설계합니다.
즉, 문제 2에서 요구되는 조회/집계를 산출할 수 있도록 필요한 필드를 payload에 정의해야 합니다.

| event_type | 발생 시점 | 비고 |
|---|---|---|
| session_login | 유저가 게임에 접속(로그인)할 때 | |
| session_logout | 유저가 접속을 종료할 때 | |
| level_up | 캐릭터가 레벨업할 때 | |
| exp_gain | 경험치를 획득할 때 | 고빈도 |
| monster_kill | 몬스터를 처치할 때 | 최고빈도 |
| quest_complete | 퀘스트를 완료할 때 | |
| item_acquire | 아이템을 획득할 때 | |
| item_use | 아이템을 사용할 때 | |
| currency_change | 게임 내 재화(골드/보석 등)가 증감할 때 | |
| shop_purchase | 상점에서 결제(구매)가 발생할 때 | |
| boss_clear | 보스를 클리어할 때 | |
| map_enter | 다른 맵/지역으로 이동할 때 | |
| death | 캐릭터가 사망할 때 | |

- 위 공통 envelope 필드와 각 이벤트 타입, payload 속성은 지원자의 판단에 따라 추가·수정·삭제할 수 있습니다. 변경한 경우 그 의도와 근거를 문서(설계 문서/README)에 명시해 주세요.

### 동작 확인용 데이터

- 적재·집계 동작을 확인할 샘플 이벤트 데이터 및/또는 생성기는 지원자가 직접 제작하여 함께 제출합니다.
- 동일 event_id가 중복으로 들어오는 케이스가 포함되도록 구성해 중복 제거가 동작함을 보일 수 있어야 합니다.
- 데이터를 어떻게 생성·적재·검증하는지 README에 적어 주세요.

## [문제1] 적재 파이프라인 설계

[공통 명세]의 전송 제약과 입력 이벤트 명세를 바탕으로 로그 적재 파이프라인의 설계 문서를 작성하여 제출합니다. 문서에는 최소한 다음 내용을 포함해 주세요.

### 아키텍처

- 전체 데이터 흐름(전송측 → 적재 진입점 → 처리 → 저장소)과 구성 요소를 기술해 주세요.
- 아키텍처 다이어그램을 포함해 주세요. 아키텍처 구조는 자유이며, 선택 근거와 트레이드오프를 함께 기술해 주세요.

### 적재 API 설계

전송측이 호출할 HTTP 적재 API를 설계해 주세요.

- 엔드포인트(경로/메서드)
- 요청 본문 형식 (전송 제약(요청 한도 120회/분, 요청 본문 4MB)을 고려한 다중 이벤트 배칭 등)
- 응답 형식
- 인증 방식
- 에러/부분 실패 응답
- 진입점은 HTTP/포트 80,443임을 전제로 합니다.

### 저장 스키마 설계

- 저장소(RDB/NoSQL/파일/기타)와 스키마, 그 선택 근거를 기술해 주세요.
- [문제2]의 집계/조회를 효율적으로 지원하도록 설계해 주세요.

## [문제2] 적재 서버 구축 & 집계/쿼리 API 구현

[문제1]에서 설계한 파이프라인을 실제로 구축하고, 적재된 데이터를 집계·조회하여 전달하는 API까지 구현하여 제출합니다. 구현 결과는 [문제1] 설계와 일관되어야 하며, 설계 대비 변경한 부분이 있다면 그 이유를 README에 남겨 주세요.

만드는 것은 다음 두 가지입니다.

1. (A) 로그 적재 서버 / 파이프라인 — [문제1]에서 설계한 적재 경로를 구현합니다.
2. (B) 집계 / 쿼리 API — (A)로 적재된 데이터를 집계·조회하여 운영자, 분석가에게 전달합니다.

### (A) 적재 서버 / 파이프라인 — 필수 요구사항

- [문제1]에서 설계한 HTTP 적재 API 계약을 그대로 구현합니다.
- 요청을 인증(토큰/API 키)으로 보호합니다.
- 같은 event_id가 여러 번 들어와도 데이터가 중복되지 않도록 처리합니다.

### (B) 집계 / 쿼리 API

적재된 데이터를 집계·조회하는 REST API를 구현합니다.

#### 필수 조회 — 핵심 지표 4종

| # | 필수 지표 | 정의 | 필요 이벤트 |
|---|---|---|---|
| 1 | DAU | 일자별 고유 접속 유저 수 | session_login |
| 2 | 리텐션 (D1/D7/D30) | 신규 유저의 N일 후 재접속 비율 | session_login (최초 접속일 기준) |
| 3 | 매출 / ARPU | 기간 내 결제 매출 합계 및 유저당 평균 매출 | shop_purchase, session_login |
| 4 | 결제 전환율 (PU/DAU) | 활성 유저 중 결제 유저 비율 | shop_purchase, session_login |

#### 요구사항

- 기간 파라미터(시작~종료)와 결과 단위(일별 등)를 지원합니다.
- 목록/시계열 응답에는 페이지네이션 또는 명확한 결과 상한이 있어야 합니다.
- 잘못된 파라미터(기간 역전, 미존재 값 등)에 대한 에러 응답을 정의합니다.
- 대용량 데이터에서도 응답이 합리적인 시간 내에 반환되도록 설계합니다.

#### 직접 제안하는 운영 지표 (가산점)

적재된 이벤트를 활용해 운영진에게 제안할 만한 지표를 지원자가 직접 정의하고 조회 API로 구현하면 가산점을 부여합니다. 지표의 정의·산출 방식과 운영상 활용 의도를 함께 기술해 주세요.

- 예: 판매된 캐시 아이템 TOP 3 순위 (shop_purchase)
- 예: 평균 경험치 획득량이 높은 맵 순위 (exp_gain)
- 예: 직업별 경험치 획득 순위 (exp_gain, level_up)
- 그 외 지원자가 가치 있다고 판단하는 지표 자유 제안

## [공통, 제출 및 안내]

### 개발 조건

- 제출 기한: 과제 안내일로부터 3일 이내
- 사용 언어: JavaScript 또는 TypeScript
- 서버 실행 환경: Node.js
- 데이터베이스: 자유
- AI 도구: 사용 가능
- 클라우드 서비스: 사용 가능

### 제출 방법

1. 지원자는 과제 진행에 사용할 GitHub 계정을 회사(평가자)에 공유합니다.
2. 평가자가 해당 계정을 과제용 GitHub Organization에 초대합니다.
3. 지원자는 권한이 부여된 리포지토리에 과제 코드를 제출합니다.

- [문제1]: 설계 문서 1부 (Markdown/PDF/슬라이드 등 형식 자유, 다이어그램 포함 권장)
- [문제2]: 적재 서버 + 집계/쿼리 API 구현 코드
- [공통]: README (빌드/실행 방법, 적재→조회 호출 예시, API 명세(또는 OpenAPI), 설계 대비 변경·가정·미구현/한계 포함)

### 평가 기준

[문제1] 설계
- 전송 제약을 정확히 이해하고 설계에 반영했는가
- 제약 하에서 적절한 설계 판단과 트레이드오프를 내렸는가
- 저장 스키마가 [문제2]의 조회 요구사항과 일관되게 맞물리는가
- 가정과 설계 의도를 문서로 명확히 전달했는가

[문제2] 구현
- [문제1] 설계를 충실히 구현했는가
- 집계/조회 API가 요구사항을 충족하고 결과가 정확한가
- 코드가 간결하고 가독성이 좋으며 구조가 합리적인가
- 테스트가 적절한 범위를 검증하는가
- 평가자가 어려움 없이 실행/호출하여 동작을 확인할 수 있는가
- (가산점) 직접 제안한 운영 지표가 운영에 유용하며, 산출 방식이 타당한가

### 안내사항

- 명세에 정의되지 않은 사항은 합리적으로 가정하고, 가정한 내용을 문서/README에 명시해 주세요.
- [문제1]의 설계는 [문제2] 구현의 기반이 되며, 두 문제는 일관되게 연결되어야 합니다.
- 모든 요구사항을 완벽히 구현하지 못하더라도, 우선순위 판단과 그 근거를 함께 보겠습니다.
- 제출한 과제는 추후 면접에서 설계·구현 결정에 대해 논의될 수 있습니다.
