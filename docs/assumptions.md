# 가정 목록 (Assumptions) — v2

> 과제 명세에 정의되지 않은 사항에 대해 본 프로젝트가 채택한 가정이다.
> 설계 문서(design.md)에서 [A-n] 형태로 참조된다.
> v2 변경: A-1, A-4, A-5, A-17, A-19 수정 / A-25~A-32 추가 (외부 설계 검토 반영)

## A. 시간과 일자

1. 모든 이벤트의 `occurred_at`은 UTC이며, 지표의 모든 기간은 **반개구간**
   `[start일 00:00:00 UTC, end일+1일 00:00:00 UTC)` 로 정의한다.
   (상한을 23:59:59.999로 두면 그 이하 정밀도의 이벤트가 제외될 수 있어 반개구간으로 통일)
   실서비스에서는 서비스 시간대(KST) 기준 일자 경계로 전환할 수 있으며, 확장 방안으로 남긴다.
2. 지표 계산은 항상 `occurred_at`(발생 시각)을 기준으로 하며, `received_at`(서버 수신 시각)은
   지연 전송·장애 분석 용도로만 사용한다.
3. 전송측 시계는 신뢰 가능한 수준으로 동기화되어 있다고 가정한다(NTP 등).
   극단적인 시계 오차 보정은 본 과제 범위에서 제외한다.

## B. 트래픽과 이벤트 발생량

4. 전체 동시접속자 300명, 인스턴스당 최대 30명이므로 논리 인스턴스 수의 **최솟값은 10개**다.
   유저 분포에 따라 활성 인스턴스는 **10~300개**까지 가능하며(극단: 인스턴스당 1명 × 300개),
   설계는 이 범위 전체를 상대한다. 인스턴스는 물리 서버와 일대일로 대응하지 않는다.
5. 유저 1명은 **평균** 초당 0.5건의 이벤트를 발생시킨다고 가정한다
   (monster_kill, exp_gain 등 고빈도 이벤트가 대부분).
   순간 피크는 평균의 10배(유저당 5건/초), 지속 시간은 최대 60초로 가정한다.
   → 전체 이벤트량은 인스턴스 분포와 무관: 평균 150건/초, 피크 1,500건/초.
6. 이벤트 1건의 직렬화 크기는 평균 약 0.5KB(최대 1KB)로 가정한다.

## C. 전송과 멱등성

7. 같은 `event_id`로 재전송되는 이벤트의 내용(payload 포함)은 동일하다.
   이 가정이 위반되어 내용이 다른 동일 event_id가 들어오면 **먼저 저장된 내용이 영구 유지**되며
   (first-write-wins), 수정된 재전송으로 기존 이벤트를 고칠 수 없다.
   적재 응답의 duplicate는 "내용 동일성을 검증한 결과"가 아니라 "event_id가 이미 존재했다"는
   의미다. (design.md §6.2)
8. 한 배치(HTTP 요청)에는 하나의 `instance_id`에 해당하는 이벤트만 포함된다.
9. 전송측은 서버의 성공 응답을 확인할 때까지 같은 event_id로 재전송하는
   at-least-once 전달을 수행한다. (송신측 구현은 문제 2 범위 밖이며 설계로만 기술)

## D. 데이터 값

10. 모든 식별자(user_id, character_id)와 금액(amount_minor)은 JavaScript의 안전한 정수 범위
    (Number.MAX_SAFE_INTEGER) 안에 있다고 가정한다.
11. 샘플 데이터의 결제 통화는 KRW만 사용한다. 스키마와 API는 다중 통화를 지원하도록
    설계하되(통화별 분리 집계), 동작 확인은 KRW 기준으로 수행한다.
12. 금액은 최소 화폐 단위 정수(`amount_minor`)로 취급한다 (9,900원 → 9900).
13. 환불(취소) 이벤트는 본 과제 범위에서 제외한다. 매출은 결제 발생 기준 총매출(gross)이다.

## E. 지표 정의 관련

14. 유저 단위 지표(DAU, 리텐션, 전환율, 참여율)는 `character_id`가 아니라 `user_id` 기준으로
    집계한다. 한 계정이 여러 캐릭터로 활동해도 1명으로 센다.
15. 리텐션은 최초 로그인 일자를 코호트로 하고, 정확히 N일 후(exact-day) 재로그인 기준으로
    계산한다. N일 이내 재접속(rolling) 방식이 아니다.
16. 조회 시점에 관찰 일자가 끝나지 않은 코호트의 Dn 값은 0%가 아니라 null로 반환한다.
    성숙(matured) 판정은 "현재 UTC 일자 > 코호트 일자 + n일", 즉 관찰 대상 일자가
    완전히 지난 후다.
17. 로그인하지 않은 유저의 게임플레이 이벤트는 발생하지 않는다고 가정한다(데이터 품질 가정).
    단, 비율 지표(전환율·참여율)의 0~100% 범위는 이 가정이 아니라
    "분자를 분모 집합과의 교집합으로 정의"하는 방식(design.md §9.4, §9.5)으로 구조적으로
    보장한다. (자정을 걸친 세션에서 로그인 일자와 활동 일자가 어긋나는 케이스 대응)
18. ARPU의 분모는 활성 유저(session_login 고유 user_id)이며, 결제 유저로 나누는 ARPPU와
    구분한다. 분모가 0인 기간의 비율/평균 지표는 null을 반환한다.

## F. API와 조회

19. 조회 기간은 양 끝 날짜를 포함해 **최대 366개 일자**로 제한한다.
20. 시계열 응답의 page_size는 최대 100으로 제한한다.
21. 인증은 인스턴스별 사전 발급 API 키(Bearer)로 수행한다. 과제 구현에서는 환경변수로
    키를 주입하며, 운영 설계에서는 키 해시 저장·회전·폐기를 전제로 기술한다.
    조회 API의 ADMIN_API_KEY는 운영자에게 별도 채널로 발급된다고 가정한다.

## G. 구현 범위

22. 구현 범위에서는 PostgreSQL에 직접 배치 적재하며 메시지 브로커(Kafka 등)는 사용하지
    않는다. 확장 경로는 설계 문서에 기술한다. (ADR-001)
23. 애플리케이션은 Controller → Service → Repository 3층 구조로 구현하며,
    Port/Adapter 추상화는 도입하지 않는다. (ADR-002)
24. TLS 종료(HTTPS 443)는 실제 배포 환경의 로드밸런서/리버스 프록시가 담당한다고 가정하며,
    로컬 실행 환경에서는 HTTP로 동작을 확인한다.

## H. v2 추가 가정 (외부 설계 검토 반영)

25. 전송측은 **순차 전송**한다: 인스턴스당 동시 진행(in-flight) 요청은 최대 1개이며,
    이전 요청의 응답(또는 timeout) 후 다음 요청을 보낸다. 요청 한도 120회/분은
    고정 1분 창(fixed window)으로 가정한다.
26. 전송측 outbox의 기록 성공은 로컬 디스크 fsync(또는 로컬 DB commit) 이후로 간주한다.
    outbox 용량 초과 시 이벤트를 삭제하지 않고 게임 로직에 backpressure를 걸어
    "유실 없음" 목표를 유지한다. 실패 저장소도 재시작 후 유지된다.
27. `order_id`는 모든 인스턴스·유저·통화에 걸쳐 **전역 유일**하다.
    같은 order_id가 다른 event_id로 재등장하는 경우 내용(user_id, 금액, 통화)은 동일하다고
    가정하며, 위반 시 먼저 저장된 결제가 유지된다(first-write-wins).
28. `amount_minor`는 상품 단가가 아니라 **주문 총액**(수량이 반영된 최종 청구 금액)이다.
    매출은 SUM(amount_minor)로 계산하며 quantity를 다시 곱하지 않는다.
29. amount_minor = 0인 shop_purchase(무료 프로모션 등)도 결제 유저(PU)에 포함한다.
30. user_id는 재사용되지 않는다(탈퇴 후 동일 ID 재발급 없음). 리텐션 코호트의 전제.
31. 모든 지표는 "조회 시점에 적재된 데이터 기준"의 **가변 결과**다. 이벤트 최대 전송
    지연이 정의되지 않았으므로, 늦게 도착한 이벤트에 의해 과거 일자의 값이 바뀔 수 있다.
    matured=true도 "관찰 일자가 달력상 끝났다"는 뜻이지 "데이터가 최종 확정됐다"는 뜻이 아니다.
32. session_login 원본 이벤트는 보존 기간 제한 없이 유지된다. (전체 이력에서 최초 접속일을
    구하는 리텐션 계산의 전제. 이벤트 삭제 정책 도입 시 코호트 스냅샷이 선행되어야 함)
