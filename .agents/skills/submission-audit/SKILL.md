# 제출 전 감사

## 목적과 담당

최종 제출 전 요구사항, 현재 코드, API, 실제 검증 증거를 대조한다.
메인 에이전트가 조율하고 docs-auditor/architecture-reviewer/metrics-reviewer는 필요한 범위만 읽기 전용 검토한다.
실제 로컬 테스트는 명시적으로 승인된 backend-developer 또는 메인 작성자가 격리 환경에서 실행한다.
문제를 고치는 스킬이 아니다. 발견한 문제는 별도 수정 작업으로 넘긴다.

## 먼저 읽을 자료

AI_RULES.md → docs/spec.md → docs/assumptions.md → docs/decisions.md →
docs/design.md → docs/api.openapi.yaml → README.md → package.json과 현재 테스트/fixture.
AWS 제출 범위가 포함되면 plan-aws.md, docs/design-aws.md, 실제 README-aws 및 해당 단계 보고를 읽는다.

## 절차

1. 검증 대상 HEAD와 미커밋 변경, 환경/Node/DB 버전, 최종 코드 지문을 확정한다.
   과제 원래 요구, AWS 후속 요구, 제안 개선을 별도 목록으로 만든다.
2. 기존 실행 증거의 코드 지문·대상 DB·명령·종료 코드를 확인한다.
   유효한 증거는 재사용하되 재실행한 것처럼 쓰지 않는다. 변경된 경로의 증거만 다시 확보한다.
3. 실행 승인 후 실제 scripts를 확인하여 lint/build/unit/e2e 및 필요한 sender 검증을 실행한다.
   --fix/스냅샷 갱신/DB 삭제 부작용을 먼저 확인한다. 실패/skip/미실행을 숨기지 않는다.
4. compose 기동 검증은 기존 볼륨 삭제 없이 별도 프로젝트명·DB·포트·볼륨으로 구성한다.
   완전 격리가 확인되지 않으면 실행하지 않는다. docker compose down -v를 관성적으로 사용하지 않는다.
   정리도 이번 실행이 소유한 자원에 한정한다.
5. README 명령을 읽고 비파괴 검증 명령과 운영 변경 명령을 분류한다.
   apply/destroy/중단/초기화/비밀값 출력 명령은 자동 실행하지 않고 사람 절차로 구분한다.
6. 중복 배치 2회 전송에서 최초 저장과 재전송 duplicate, 원본/매출 불변을 확인한다.
   seed/demo는 기존 fixture 기대값을 사용하고 검증용 별도 DB에서만 실행한다.
7. DAU/리텐션/매출·ARPU/전환율/참여율의 기간·summary·교집합·matured·null·zero-fill을 대조한다.
   단순 테스트 개수만으로 지표 정의 일치를 판정하지 않는다.
8. 인증 401, 키-인스턴스 403, 파라미터 400, 적재 429+Retry-After와 계약상 에러를 확인한다.
   DB 오류 503과 HTTP 데드라인 후 커밋 가능성을 구분한다.
9. 실제 TypeORM Entity/마이그레이션/CHECK·인덱스·PK와 문서를 대조한다.
   오래된 Prisma schema나 오류 코드를 현재 구현의 근거로 삼지 않는다.
10. design.pdf/SVG/Markdown의 최신성 또는 과거 제출 스냅샷 표기를 확인한다.
    일치 여부를 확인할 수 없으면 NOT_RUN으로 남긴다. 기존 PDF를 임의 재생성하지 않는다.
11. tracked 파일/예시 설정에서 .env/토큰/원본 outbox/state/plan 노출을 확인한다.
    시크릿을 발견하면 값은 가리고 경로·위험만 보고한다. 이 감사에서 기록을 삭제하지 않는다.
12. 가정·한계·미완료·로컬 대 AWS 수치·사용 도구 및 검토 범위의 정직성을 확인한다.

## 완료 보고

항목 / 기준 파일·절 / PASS·FAIL·BLOCKED·NOT_RUN / 명령·종료 코드 / 증거 / 담당 표.
최종 제출 가능 여부와 사람이 결정할 사항을 구분한다.
필수 실행이 빠졌으면 ‘감사 완료, 제출 검증 미완료’처럼 상태를 나누고 전체 PASS라고 하지 않는다.

## 공통 실행 경계 — 스킬 호출이 권한을 확대하지 않는다

- 적용되는 AGENTS.md/하위 지침과 AI_RULES.md를 우선 확인한다. 현재 요청이 허용한 단계·파일만 다룬다.
- 먼저 git 브랜치/HEAD/status와 기존 변경·실행 프로세스를 확인한다. 기존 수정·데이터·증거를 보존한다.
- 메인이 작업을 조율하고 작성자는 동시에 1명만 둔다. 리뷰어는 파일/테스트를 수정하지 않는다.
  이 스킬을 읽었다고 에이전트가 자동 생성되는 것은 아니다. 실제 위임할 때 역할·경로·검증 범위를 전달한다.
- terraform apply/destroy는 사람이 실행한다. CLI/SDK/terraform test/provisioner로 우회하지 않는다.
  자격 증명·backend·입력 부재를 가짜 값으로 메우지 않는다. 운영 대상 변경은 별도 승인 없이는 하지 않는다.
- 시크릿 값은 조회·출력·커밋하지 않는다. 인스턴스 runtime 주입용 코드는 이름/ARN과 IAM만 다룬다.
- DB 초기화·부하·서비스 중단은 정확한 계정/환경/대상/범위와 복구 계획에 대한 명시적 승인 후에만 한다.
- 단계 표의 완료 조건을 임의 완화하지 않는다. 읽기/코드 작성/정적 검증/plan 리뷰/사람 apply/실측을 분리한다.
- 근거는 현재 저장소와 실행 로그다. 오래된 첨부본으로 최신 T3 보고·design-aws.md를 덮어쓰지 않는다.
- 결과는 PASS/FAIL/BLOCKED/NOT_RUN으로 구분한다. 실행한 명령·종료 코드·시각·버전·증거 경로를 적는다.
- 원래 과제/기획과 충돌하는 안전상 보강·새 선택은 제안으로 표시하고 사람이 기준 문서를 정리하기 전 강행하지 않는다.
- 별도 요청 없이 git add/commit/push나 브랜치 조작을 하지 않는다.
