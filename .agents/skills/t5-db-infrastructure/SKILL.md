# T5 DB 인프라

## 기획의 범위와 완료 조건

원문 범위: EC2 + user_data(PostgreSQL 16 설치·초기화), gp3 EBS, 스냅샷·pg_dump 백업, chrony.
원문 완료 조건: receiver에서 psql 접속 확인.

## 담당과 상태 구분

infra-developer는 승인된 infra/ 코드만 작성한다. infra-reviewer는 읽기 전용 검토한다.
다른 경로 문서 갱신은 메인의 별도 승인 범위다. apply/destroy는 사람만 실행한다.
‘receiver에서 psql’은 T6 receiver 생성에 의존한다. 아직 없으면 원래 완료 조건을 유지한 채
‘T5 코드/plan 완료, receiver 연결 실측 대기’로 보고한다. 임의 테스트 EC2를 만들거나
다른 호스트의 psql 결과를 receiver 증거로 대체하지 않는다. 단계 이동 승인은 사람이 한다.

## 읽기·입력

AI_RULES.md, plan-aws.md T5·D1~D6, docs/design-aws.md §6·§7·§9·§12,
docs/design.md의 스키마·트랜잭션 절, 실제 infra/와 T4 검증·승인·사람 적용 기록.
AMI/CPU 구조, DB 인스턴스 타입, EBS 용량, PG16 패키지 공급,
SSM·chrony 공급/통신, DB명·역할명·시크릿 경로, 백업 대상·주기·보존·암호화,
삭제/복구 정책을 확보한다. 원문의 TBD를 승인 없이 기본값으로 확정하지 않는다.

## 절차

1. T4 네트워크/SG/IAM/Endpoint 출력과 실제 적용 상태를 확인한다. 앱 코드를 바꾸지 않는다.
2. DB 인터넷 격리와 user_data 설치 경로를 먼저 검증한다.
   오프라인 아티팩트/내부 공급 경로 또는 사전 준비 이미지가 필요하면 제안으로 보고한다.
   사전 이미지 방식은 원문의 설치 방식에 영향을 줄 수 있으므로 문서 승인 없이 대체하지 않는다.
   임시 NAT/공개IP/SSH를 추가하지 않는다. SSM 연결이 곧 패키지 공급 가능성을 뜻하지 않는다.
3. DB EC2와 gp3 데이터 볼륨, mount 의존 관계, Project 태그, 승인된 IAM을 구현한다.
   볼륨 ID/기존 파일시스템/데이터를 확인하지 않고 mkfs/initdb하지 않는다.
   mount 실패 때 root 디스크의 빈 디렉터리에 DB를 초기화하지 않도록 실패 처리한다.
4. user_data는 PG16 설치·최초 초기화·재실행·재부팅을 구분한다.
   기존 데이터가 있으면 초기화를 생략하고, 다른 버전/손상은 자동 삭제하지 말고 실패한다.
   runtime에서만 시크릿을 가져오며 shell trace·cloud-init 로그·프로세스 인자에 남기지 않는다.
5. 앱 전용 계정, 원격 superuser 차단, 승인된 접속 범위/인증 방식,
   UTF8/UTC 설정과 서비스 시작 순서를 정리한다. trust 인증이나 전역 허용으로 접속을 뚫지 않는다.
   앱 스키마/데이터의 배포는 실제 TypeORM 마이그레이션 절차를 사용한다.
   synchronize로 운영 스키마를 자동 수정하거나 T1 migration을 재작성하지 않는다.
6. chrony와 SSM Agent의 기동/실패 감지, PostgreSQL 서비스 상태와 cloud-init 진단 위치를 문서화한다.
7. EBS 스냅샷과 pg_dump 백업을 원문대로 준비한다. 보존 기간/주기는 승인된 값을 쓴다.
   업로드·보존·오류 감지·복구 대상·DB 역할/권한 복구 범위·IAM/네트워크를 함께 검토한다.
   백업 파일이나 스냅샷이 있다는 사실만으로 복구 검증 완료로 보고하지 않는다.
8. fmt/validate/안전한 shell 구문 검사/실제 plan을 수행하고 삭제·교체·데이터 보존을 리뷰한다.
   user_data나 복구 스크립트를 개발 머신에서 직접 실행하지 않는다.
9. 사람 apply 후 승인된 검증에서 PG16 버전/마운트/SSM/chrony를 확인하고,
   receiver가 준비되면 receiver→DB 실제 psql 연결과 최소 SELECT를 확인한다.
   실제 비밀번호는 보고서·CLI 인자에 기록하지 않는다.

## 산출물·완료 판정

변경 파일, 명령·종료 코드, plan 생성/변경/삭제/교체, 비용 변화,
DB/volume/backup 출력, 사람 실행·복구 절차, receiver 접속 증거 또는 대기 사유.
DB/EBS를 파괴해 재생성하는 테스트는 이 스킬의 자동 실행 대상이 아니다.

## 공통 실행 경계 — 스킬 호출이 권한을 확대하지 않는다

- 적용되는 AGENTS.md/하위 지침과 AI_RULES.md를 우선 확인한다. 현재 요청이 허용한 단계·파일만 다룬다.
- 먼저 git 브랜치/HEAD/status와 기존 변경·실행 프로세스를 확인한다. 기존 수정·데이터·증거를 보존한다.
- 메인이 작업을 조율하고 작성자는 동시에 1명만 둔다. 리뷰어는 파일/테스트를 수정하지 않는다.
  이 스킬을 읽었다고 에이전트가 자동 생성되는 것은 아니다. 실제 위임할 때 역할·경로·검증 범위를 전달한다.
- terraform apply/destroy는 사람이 실행한다. CLI/SDK/terraform test/provisioner로 우회하지 않는다.
  자격 증명·backend·입력 부재를 가짜 값으로 메우지 않는다. 운영 대상 변경은 별도 승인 없이는 하지 않는다.
- 시크릿 값은 조회·출력·커밋하지 않는다. 인스턴스 runtime 주입용 코드는 이름/ARN과 IAM만 다룬다.
- DB 초기화·부하·서비스 중단은 정확한 계정/환경/대상/범위와 복구 계획에 대한 명시적 승인 후에만 한다.
- 단계 표의 완료 조건을 임의 완화하지 않는다. 읽기/코드 작성/정적 검증/plan 리뷰/사람 apply/실측을 분리한다.
- 근거는 현재 저장소와 실행 로그다. 오래된 첨부본으로 최신 T3 보고·design-aws.md를 덮어쓰지 않는다.
- 결과는 PASS/FAIL/BLOCKED/NOT_RUN으로 구분한다. 실행한 명령·종료 코드·시각·버전·증거 경로를 적는다.
- 원래 과제/기획과 충돌하는 안전상 보강·새 선택은 제안으로 표시하고 사람이 기준 문서를 정리하기 전 강행하지 않는다.
- 별도 요청 없이 git add/commit/push나 브랜치 조작을 하지 않는다.
