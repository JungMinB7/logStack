# T8 AWS 실측·장애 시연·재현성

## 기획의 범위와 완료 조건

원문 범위: AWS load-check, 장애 A(receiver 60초 정지)/B(DB 정지)/C(1대 스로틀 해제→429),
각 시나리오 생성 총건수=DB 저장 건수·유실0, 다이어그램/README-aws, destroy→apply 리허설.
원문 완료 조건: infra-audit 통과, 15분 내 재현, 장애 3종 결과 기록.

## 담당·실행 승인

메인이 실측을 조율한다. infra/ runbook은 infra-developer,
검증 하네스/관련 문서는 별도 승인된 backend-developer 또는 메인 작성자,
검토는 infra-reviewer와 필요한 architecture/metrics/docs 역할에 맡긴다.
작성자는 한 번에 1명이다. terraform apply/destroy는 이 단계에서도 사람만 실행한다.
스킬 호출만으로 운영 장애 주입을 승인받은 것으로 간주하지 않는다.

## 입력·사전 계획

AI_RULES.md, plan-aws.md T8, docs/design-aws.md §7·§9·§10·§12,
T3 로컬 보고와 T4~T7 실제 적용·검증, 현재 load-check/관측 도구를 읽는다.
AWS 계정/리전/대상 EC2·서비스·DB, 허용 부하·시간, 복구 담당/절차,
관측·중단 임계치, run_id·논리 인스턴스 목록, 생성/기록 성공 기준을 확정한다.
대상·되돌리기·데이터 영향이 불명확하면 계획만 보고하고 멈춘다.

## 검증 기준

- 정상 입력의 최종 기준은 G=D, F=0, pending=0이다. 원문의 생성=DB 조건을
  ‘실패 저널로 이동했으니 성공’으로 완화하지 않는다.
- G는 해당 실행의 fsync 이후 기록 성공한 독립 event_id 집합, D는 해당 run의 game_events,
  F는 내구성 실패 저널이다. 생성 시도/기록 성공/미기록 수와 raw/unique 수를 모두 기록한다.
- 집합 missing/unexpected/overlap·중복을 확인하고 각 인스턴스 및 10대 전체를 대조한다.
  별도 run 데이터 구분은 기존 envelope/인스턴스·ID 증거로 한다. 편의를 위해 API 필드를 추가하지 않는다.
- ACK 카운트 합이나 DB 전체 COUNT만으로 검증하지 않는다. 기대 ID를 DB/ACK에서 역생성하지 않는다.
  컴팩션 뒤에도 독립 기대 집합을 보존한다. 정상 복구 후 생성 종료·최종 drain 기준 시각을 나눈다.

## 시나리오 — 사람의 해당 실행 승인 후

1. 기준 부하: 기존 load-check의 입력·총 요청·성공 정의·p50/p95·실패 유형·자원 상태를 기록한다.
   로컬 값과 AWS 값을 나란히 기록하되 AWS 실측을 로컬 환산으로 대신하지 않는다.
2. A: receiver만 정확히 60초 정지하고 sender는 계속 기록한다.
   실제 정지 구간, ALB/전송 오류, 최대 outbox, 재기동/health 복구/정상 적체 회복/최종 drain 시간을 나눈다.
   ALB 오류 상태와 애플리케이션 상태를 구분하고 9초 같은 설계 계산을 실제 상한으로 강요하지 않는다.
3. B: DB만 정지하고 receiver는 유지한다. 실제 503과 sender 백오프를 관측한다.
   T1 이후 실제 TypeORM/pg 오류 경로를 확인한다. Prisma 오류 코드가 나왔다고 가정하지 않는다.
   DB 재기동 후 같은 ID 재전송·중복 흡수·최종 정합을 확인한다.
   HTTP 데드라인 503만으로 ‘커밋 안 됨’이라고 판정하지 않는다.
4. C: 승인된 1대에서만 자체 스로틀을 임시 해제한다. 서버의 정상 120회/분 한도를
   낮추는 다른 실험으로 바꾸지 않는다. 인증을 통과한 실제 요청으로 429를 유도한다.
   해제만 했는데 1초 배칭 때문에 120회를 넘지 못하면, 원인과 필요한 적체/부하 조건을
   먼저 제시하고 승인받는다. 429가 없는데 성공이라고 쓰지 않는다.
   Retry-After 수신 시각과 다음 실제 요청 시작을 비교하고 jitter 포함 대기를 확인한다.
   고정 창/반복 재시작 한계를 분리하고, 끝나면 1대의 임시 설정을 복원해 확인한다.
5. 각 시나리오 후 정상 상태와 G=D/F=0/pending=0을 확인한다.
   한 시나리오가 복구되지 않은 상태에서 다음 장애를 겹쳐 실행하지 않는다.
   중단 시에도 데이터를 지우지 말고 상태·복구 담당·미완료 증거를 남긴다.

## 재현성·문서

6. destroy 대상과 보존 대상(상태/키/DNS·인증서/백업 등), 최초 준비,
   15분 측정의 시작·종료와 포함/제외 범위를 사람이 사전에 확정한다.
   기준을 사후 바꾸거나 오래 걸린 준비 시간을 몰래 빼지 않는다.
7. infra-audit로 실제 plan과 보존·삭제 영향을 검토한다. 사람은 승인된 runbook으로 destroy/apply를 실행한다.
   AI가 버튼/SSM/CLI를 대신 실행하지 않는다. 사람 실행 로그를 수집하여 최종 10대 유입까지 측정한다.
   인스턴스 실행 상태만으로 전체 파이프라인 재현 완료 처리하지 않는다.
8. README-aws와 다이어그램을 실제 구성·명령·값에 맞춰 승인된 범위에서 갱신한다.
   원본 요구 문서/spec·기존 T3 증거는 바꾸지 않는다. 비밀 제거 요약만 커밋 후보로 남긴다.

## 산출물·판정

환경·코드·run_id, 부하 결과, A/B/C별 승인·명령·UTC 시각·오류·대기·적체·회복·집합 정합,
15분 재현 타임라인, infra-audit 결과, 복원 상태, 한계와 미검증 항목.
실제로 하지 않은 장애/리허설은 NOT_RUN이다. 표 양식을 채운 것만으로 T8 완료라 하지 않는다.

## 공통 실행 경계 — 스킬 호출이 권한을 확대하지 않는다

- 적용되는 AGENTS.md/하위 지침과 AI_RULES.md를 우선 확인한다. 현재 요청이 허용한 단계·파일만 다룬다.
- 먼저 git 브랜치/HEAD/status와 기존 변경·실행 프로세스를 확인한다. 기존 수정·데이터·증거를 보존한다.
- 메인이 작업을 조율하고 작성자는 동시에 1명만 둔다. 리뷰어는 파일/테스트를 수정하지 않는다.
  이 스킬을 읽었다고 에이전트가 자동 생성되는 것은 아니다. 실제 위임할 때 역할·경로·검증 범위를 전달한다.
- terraform apply/destroy는 사람이 실행한다. CLI/SDK/terraform test/provisioner로 우회하지 않는다.
  자격 증명·backend·입력 부재를 가짜 값으로 메우지 않는다. 운영 대상 변경은 별도 승인 없이는 하지 않는다.
- 시크릿 값은 조회·출력·커밋하지 않는다. 인스턴스 runtime 주입용 코드는 이름/ARN과 IAM만 다룬다.
- DB 초기화·부하·서비스 중단은 정확한 계정/환경/대상/범위와 복구 계획에 대한 명시적 승인 후에만 한다.
- 단계 표의 완료 조건을 임의 완화하지 않는다. 읽기/코드 작성/정적 검증/plan 리뷰/사람 apply/실측을 분리한다.
- 근거는 현재 저장소와 실행 로그다. 오래된 첨부본으로 최신 T3 보고·design-aws.md를 덮어쓰지 않는다.
- 결과는 PASS/FAIL/BLOCKED/NOT_RUN으로 구분한다. 실행한 명령·종료 코드·시각·버전·증거 경로를 적는다.
- 원래 과제/기획과 충돌하는 안전상 보강·새 선택은 제안으로 표시하고 사람이 기준 문서를 정리하기 전 강행하지 않는다.
- 별도 요청 없이 git add/commit/push나 브랜치 조작을 하지 않는다.
